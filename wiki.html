TSCAT SOAP API Tests

Validación automatizada de los endpoints del servicio GSITWebService mediante Karate y el patrón Golden File.

¿Qué es este proyecto?

Suite de tests de regresión para el servicio SOAP GSITWebService (aggregator) de la plataforma TSCAT/GSIT. Cada test llama a un endpoint real, captura la respuesta XML completa y la compara contra una respuesta de referencia previamente guardada (golden file).

Ante cualquier cambio inesperado en un endpoint —un campo que desaparece, un valor que cambia, una estructura que se modifica— el test correspondiente falla, alertando del cambio antes de que llegue a producción.

Stack técnico
Java 17 · Maven 3 · Karate 1.4.1 · JUnit 5 · GraalVM 24.1.1

Arquitectura

El servicio expone un único método WSDL (aggregator) que actúa como enrutador: el campo Operation del body determina qué lógica se ejecuta. Cada operación es, en la práctica, un endpoint independiente.

Patrón Golden File

Un golden file es una respuesta real grabada en un momento en que el sistema está correcto. En ejecuciones posteriores, la respuesta actual se compara contra ese fichero: si coinciden, el test pasa; si difieren, falla.

Flujo de ejecución (por feature)

1
HTTP POST al endpoint SOAP Karate envía el body XML de requests/ con las cabeceras Content-Type: text/xml y SOAPAction.
2
Then status 200 Falla inmediatamente si el servidor devuelve cualquier código distinto de 200.
3
Normalización del XML soap-helpers.js::normalizeXml(dynamicPaths) obtiene los bytes del response, lo parsea con un DOM, reemplaza los XPaths configurados en dynamicPaths por el token __DYNAMIC__ y serializa el árbol con indentación uniforme.
4
Record o compare En modo record: guarda el XML normalizado como golden file.
En modo compare: carga el golden file y lo compara con match actualXml == expectedXml (comparación estructural nodo a nodo).

Campos dinámicos

Algunos campos del response cambian en cada llamada (timestamps, IDs de sesión, fechas de creación…). Si se incluyeran en la comparación, los tests fallarían siempre aunque el contrato del servicio no haya cambiado.

Cada feature expone un array dynamicPaths en su Background. Añade las expresiones XPath de los campos que deban ignorarse:

# En el Background del feature correspondiente:
* def dynamicPaths = ['//dataCreacio', '//timestamp', '//@sessionId']

El helper reemplazará el contenido de esos nodos por __DYNAMIC__ en ambos XMLs (actual y golden) antes de compararlos.

Importante: re-graba el golden tras añadir dynamicPaths
Si añades un nuevo XPath a dynamicPaths, el golden file existente aún contiene el valor real. Ejecuta -Dmode=record para regenerarlo con el token __DYNAMIC__.

Comandos Maven

Primera ejecución — grabar golden files

mvn test -Dtest=SoapTest -Dmode=record

Llama a los 10 endpoints contra preprod y guarda las respuestas XML normalizadas en src/test/java/tscat/soap/golden/. Commitalos al repositorio.

Ejecución normal — comparar

mvn test -Dtest=SoapTest

Llama a los 10 endpoints y compara cada respuesta contra su golden file. Si algún campo difiere, el test falla indicando el nodo exacto.

Ejecutar un único test

mvn test -Dtest=SoapTest -Dkarate.options="classpath:tscat/soap/confConvoLang.feature"

Regenerar un golden file concreto

mvn test -Dtest=SoapTest -Dmode=record -Dkarate.options="classpath:tscat/soap/confConvoLang.feature"

Añadir un nuevo test

1
Crea el request XML Copia el body SOAP de SoapUI y guárdalo en src/test/java/tscat/soap/requests/miOperacion.xml.
2
Crea el feature Copia cualquier .feature existente, actualiza goldenFile, la URL (soapWsUrl o soapGfUrl) y el request.
3
Graba el golden file mvn test -Dtest=SoapTest -Dmode=record -Dkarate.options="classpath:tscat/soap/miOperacion.feature"
4
Commitea el golden file El fichero de golden/ es parte del código fuente — sin él, el test no puede comparar.
